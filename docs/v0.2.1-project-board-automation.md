# Sway Forge v0.2.1 — Project Board Automation

## Release objective

Make the GitHub Project the reliable live control room for Sway Forge development before v0.3.0 begins.

The Project must let the user see, at a glance:

- Ideas
- Backlog
- Planned work
- Work in progress
- Work awaiting review
- Completed work
- Priority
- Complexity
- Type
- Target release
- Functional area
- Actual implementation branch
- Actual start date
- Target date where genuinely scheduled

This release reduces manual bookkeeping and prepares Sway Forge for increasingly autonomous release-by-release development while preserving explicit review and merge control.

## Lifecycle

`Idea -> Backlog -> Planned -> In Progress -> Review -> Done`

## Board fields

Canonical field order:

1. Priority
2. Complexity
3. Title
4. Status
5. Type
6. Target Release
7. Area
8. Branch
9. Start Date
10. Target Date

### Branch

`Branch` means the real implementation branch and is populated only once that branch exists.

Planned branch names remain visible in the Issue/Index before commencement. If pre-start branch visibility is required directly on the Project, add a separate `Planned Branch` field rather than presenting a nonexistent branch as active.

### Start Date

Populate only with the actual date implementation begins.

### Target Date

Populate when work has genuinely been scheduled. Do not invent dates simply to fill the board.

## Full-board backfill

v0.2.1 must reconcile the existing Sway Forge roadmap into the Project so the board is complete, not merely correct for future Issues.

The backfill must cover:

- completed v0.1.0 work;
- completed v0.2.0 work;
- v0.2.1 itself;
- planned v0.3.0 through v1.0.0 work;
- unscheduled/backlog/idea work where represented by canonical Issues.

For every eligible Issue, populate all values that are actually known.

Unknown/uncommitted dates must remain blank rather than fabricated.

## Automatic lifecycle synchronization

### Planned -> In Progress

Only after development actually commences and the dedicated branch exists. Set Status, Branch and Start Date together with the Issue/Index transition.

### In Progress -> Review

Only after implementation/testing complete, changes are committed/pushed and the draft PR is ready.

### Review -> Done

Only after the user reviews and merges the PR and the merge is verified.

Automation must never merge merely to advance status.

## Technical approach

Implement an idempotent GitHub Projects v2 synchronization script plus GitHub Actions workflow that can:

- discover the configured Project and fields dynamically;
- ensure eligible Issues appear in the Project;
- reconcile all canonical fields;
- perform a complete manual full-board rebuild/backfill;
- perform focused sync after supported Issue/PR events;
- produce dry-run/audit output;
- fail safely if Project fields/options are missing or renamed;
- never expose Project credentials in logs.

## Authentication

Project access credentials belong only in GitHub Actions Secrets or an appropriately permissioned GitHub App.

Never commit, log or place a PAT/token in Issue bodies, repository files or ordinary configuration.

## User-control boundary

The Project is a planning and visibility surface. It does not grant publishing, release, merge or social-account authority.

Existing Sway Forge rules remain authoritative:

- no direct work on `main`;
- one substantial Issue per branch;
- test before review;
- draft PRs;
- user reviews and merges;
- only then mark Done;
- no release publication unless explicitly instructed.

## Acceptance criteria

- [ ] GitHub Project shows the complete current roadmap rather than only newly-created work.
- [ ] Idea, Backlog, Planned, In Progress, Review and Done are visibly distinguishable.
- [ ] Priority, Complexity, Type, Target Release and Area are populated from canonical planning metadata.
- [ ] Actual Branch and Start Date appear automatically once development begins.
- [ ] Target Date is populated only from genuine scheduling data.
- [ ] Existing completed work is backfilled accurately.
- [ ] Future Project changes are synchronized automatically and idempotently.
- [ ] Missing/renamed fields fail visibly without corrupting the board.
- [ ] No Project token/credential is committed or logged.
- [ ] The system supports future release-by-release autonomous development tracking while retaining user review/merge authority.
